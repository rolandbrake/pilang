# 14.7 Acknowledgements

Pilang is built on the ideas, tools, and practices shared by many language communities.

## Language Design

Pilang draws from familiar dynamic-language ideas:

- first-class functions and closures
- maps as flexible object-like values
- classes and prototype-style behavior
- iterable collections
- concise arrow functions
- module imports and aliases
- batteries-included built-in modules

The documentation uses examples that should feel approachable to programmers coming from languages such as Python, JavaScript, Lua, and other dynamic runtimes.

## Runtime And Tooling

The runtime architecture uses classic interpreter and VM techniques:

- scanning source into tokens
- parsing tokens into language structures
- compiling to bytecode
- executing bytecode on a stack VM
- managing function calls with frames
- preserving closures with upvalues
- reclaiming memory with garbage collection

These ideas are part of a long tradition of language implementation work.

## Libraries And Platforms

Pilang's native and graphical features depend on platform libraries and toolchains. The project includes integration points for native execution and browser-oriented builds.

The documentation also acknowledges the importance of:

- C toolchains
- SDL-based graphics infrastructure
- Emscripten-style browser builds
- terminal and filesystem APIs

## Documentation

This documentation was organized to make Pilang easier to learn incrementally:

1. start with introduction and syntax basics
2. build up through data types, operators, control flow, and functions
3. move into objects, modules, memory, and advanced topics
4. end with examples and references

The goal is to serve both new users and people extending the language.

## Contributors

Thanks to everyone who designs, tests, documents, reviews, debugs, and improves Pilang. Language projects grow through small careful corrections as much as through large features.

Special acknowledgement goes to the maintainers and users who notice details such as syntax accuracy, edge cases, naming conventions, and examples that should be clearer.
