# 8.3 Module Paths

Module paths use dot-separated names.

```swift
import math
import tests.module.private_module
```

Dots are converted to path separators when resolving user modules.

```text
tests.module.private_module -> tests/module/private_module.pi
```

## Resolution Order

When Pilang imports a module, it resolves the name in layers. Earlier layers win
over later layers.

1. A user-defined `.pi` module relative to the current module's directory.
2. A user-defined `.pi` module matching the path from the current working area.
3. A shared predefined `.pi` module under the project `libs` directory.
4. A native built-in module with that name.

This means local source files have priority over shared library modules, and
shared library modules have priority over built-ins.

```text
import math

1. ./math.pi relative to the importing module
2. math.pi from the current working area
3. libs/math.pi
4. built-in module named math
```

If `math.pi` exists next to your current file, Pilang imports that file instead
of the built-in `math` module. If no user or `libs` file exists, Pilang falls
back to the built-in module table.

## Relative to the Current Module

Imports inside a module are resolved relative to that module's directory.

```text
project/
  main.pi
  tools/
    strings.pi
    parse.pi
```

From `tools/parse.pi`, a nearby import can reference another file in the same
module area.

```swift
import strings
```

That import first looks for:

```text
project/tools/strings.pi
```

This is why modules can use simple nearby imports without spelling the whole
project path.

## Current Working Area Fallback

After the nearby-module check, Pilang also checks for a `.pi` file matching the
module path from the current working area.

```swift
import tools.parser
```

The dotted path is normalized to:

```text
tools/parser.pi
```

This fallback is useful for entry scripts run from a project root.

## The `libs` Directory

If no nearby or working-area user module is found, Pilang checks the `libs`
directory.

```text
libs/<module-path>.pi
```

For example:

```swift
import text.slug
```

can resolve to:

```text
libs/text/slug.pi
```

Use `libs` for shared Pilang modules that should be available to many scripts
without copying them next to each script.

## Built-in Module Names

Built-in modules are checked last. They are native modules compiled into the
runtime. Built-in modules use simple names such as:

- `math`
- `string`
- `fs`
- `sys`
- `tensor`
- `time`
- `col`
- `func`

See [Built-in Modules](8.4%20Built-in%20Modules/README.md) for the full list.

Because built-ins are checked last, a user file can shadow a built-in name.

```text
project/
  main.pi
  math.pi
```

In `main.pi`:

```swift
import math
```

loads `project/math.pi`, not the built-in `math` module. To avoid confusion,
avoid naming local modules the same as built-ins unless shadowing is intentional.

## File Extension

Imports use module names, not file extensions.

```swift
import tools.parser
```

The source file is resolved as a `.pi` file when a user module is loaded.

## Private Module Members

The path itself can point to a file with private names, but members beginning
with `_` cannot be imported or accessed from outside the module.
