# 8.5 User Modules

A user module is a `.pi` file imported by another Pilang file.

```text
project/
  main.pi
  calculator.pi
```

```swift
// calculator.pi
fun add(a, b) {
    return a + b
}

fun sub(a, b) {
    return a - b
}
```

```swift
// main.pi
import calculator

println(calculator.add(2, 3))
```

## Public API

The public API of a user module is made of its top-level names that do not start
with `_`.

```swift
let version = "1.0"
let _cache = {}

fun parse(text) {
    return text
}

fun _helper() {
    return "internal"
}
```

This module exports `version` and `parse`. It does not export `_cache` or
`_helper`.

## Import Styles

User modules support the same import forms as built-in modules.

```swift
import calculator
import calculator:add_math
import calculator.{add, sub}
import calculator.{add:plus}
import calculator.*
```

Use wildcard imports carefully because they write many names into the current
module/global scope.

## Module Objects

A plain import gives you a module object.

```swift
import calculator

println(calculator.name)
println(calculator.path)
println(calculator.exports)
```

Access exports with dot syntax:

```swift
println(calculator.add(10, 20))
```

## Module State and Caching

Imported modules are cached. If two files import the same resolved module, they
share the same module instance and the same module globals.

```swift
// ids.pi
let current = 0

fun next() {
    current = current + 1
    return current
}
```

```swift
import ids

println(ids.next()) // 1
println(ids.next()) // 2
```

## Designing User Modules

Prefer a small public surface:

- export functions, classes, constants, and module-level objects intentionally
- prefix implementation details with `_`
- use selected imports in consumers when only a few names are needed
- avoid wildcard imports in shared modules
- keep module-level mutable state deliberate, because it is shared through the
  import cache
