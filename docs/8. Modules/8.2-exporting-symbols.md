# 8.2 Exporting Symbols

Pilang user modules export top-level names automatically. There is no separate
`export` statement.

```pilang
// math_tools.pi
let pi2 = 6.28318

fun square(n) {
    return n * n
}
```

Another file can import those names:

```pilang
import math_tools

println(math_tools.pi2)
println(math_tools.square(5))
```

## What Gets Exported

Top-level globals defined by a module become public exports.

```pilang
let name = "tools"

fun double(n) {
    return n * 2
}

class Box {
    constructor(value) {
        this.value = value
    }
}
```

This module exports `name`, `double`, and `Box`.

## Private Names

A top-level name that starts with `_` is private.

```pilang
let visible = 42
let _hidden = 99

fun public_api() {
    return _hidden + visible
}
```

The module exports `visible` and `public_api`, but not `_hidden`.

Private names can still be used inside the same module.

## Importing Private Names

Outside code cannot import or access private names.

```pilang
import tools

println(tools.visible)

// Invalid
println(tools._hidden)
```

Private names are also skipped by wildcard imports.

```pilang
import tools.*

println(visible)
// _hidden was not imported
```

## Module State

Top-level variables live in the module's global scope. Functions imported from a
module keep access to that module's globals.

```pilang
// counter.pi
let count = 0

fun next() {
    count = count + 1
    return count
}
```

```pilang
import counter

println(counter.next()) // 1
println(counter.next()) // 2
```

Because modules are cached, this state is shared by all imports of the same
resolved module path.

## The `module` Variable

Inside an imported file, `module` refers to the current module object.

Useful fields include:

- `module.name`: the import name
- `module.path`: the resolved source path when available
- `module.is_main`: whether this module is the entry module
- `module.exports`: the map of public exports
