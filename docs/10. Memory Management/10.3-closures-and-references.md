# 10.3 Closures and References

Closures can keep variables and objects alive after the scope that created them
has returned.

```pilang
fun make_counter() {
    let count = 0

    return () -> {
        count = count + 1
        return count
    }
}

let counter = make_counter()
println(counter()) // 1
println(counter()) // 2
```

The variable `count` remains alive because the returned function captured it.

## Captured Variables

When an inner function uses a local variable from an outer function, Pilang stores
that captured value in an upvalue. The closure references the upvalue, so the
captured value stays reachable.

```pilang
fun make_adder(amount) {
    return value -> value + amount
}

let add10 = make_adder(10)
println(add10(5)) // 15
```

`amount` survives after `make_adder` returns because `add10` still needs it.

## Capturing Objects

Closures keep captured objects alive too.

```pilang
fun make_store() {
    let data = {}

    return {
        set(key, value) {
            data[key] = value
        },
        get(key) {
            return data[key]
        }
    }
}

let store = make_store()
store.set("name", "Ada")
println(store.get("name"))
```

The `data` map remains alive through the methods that captured it.

## Shared Captures

Multiple closures can share the same captured variable.

```pilang
fun make_pair() {
    let value = 0

    return {
        inc() {
            value = value + 1
            return value
        },
        get() {
            return value
        }
    }
}

let pair = make_pair()
println(pair.inc()) // 1
println(pair.get()) // 1
```

Both methods refer to the same captured `value`.

## Releasing Captured Data

A captured object remains alive as long as the closure that references it remains
alive. To allow collection, release the closure or clear the captured structure.

```pilang
let store = make_store()

// Later, when the store is no longer needed:
store = nil
```

If a closure captures a large map or list, keeping the closure in a global cache
also keeps that data alive.

```pilang
let handlers = []

fun register_big_handler() {
    let data = [1, 2, 3]

    push(handlers, () -> len(data))
}
```

The list stays alive because `handlers` keeps the closure alive.

## Globals and Accidental References

Remember Pilang's assignment rule: assigning to a new name inside a local scope
without `let` creates or updates a module/global variable. That global can keep
objects alive longer than intended.

```pilang
fun build() {
    data = [1, 2, 3] // global/module variable, not local
}
```

Prefer `let` for temporary local values:

```pilang
fun build() {
    let data = [1, 2, 3]
}
```

## Closures and Methods

Methods are functions, so they can capture outer variables just like ordinary
functions.

```pilang
fun make_box(secret) {
    return {
        reveal() {
            return secret
        }
    }
}

let box = make_box("pi")
println(box.reveal())
```

The returned object keeps its method alive, and the method keeps `secret` alive.
