# 12.5 Packaging System

Pilang currently uses a module-based organization model. A full package manager with manifests, version solving, downloads, and lockfiles is separate from the core module system and may be added as tooling around it.

This page describes how to organize code today and what a future packaging layer should preserve.

## Current module model

Pilang modules are source files or built-in modules that can be imported.

```pilang
import math:m
import utils:u
```

The VM resolves module paths, loads modules, caches them, and exposes their exports.

Each loaded module tracks:

- module name
- resolved path
- whether it is built-in
- whether it is the main entry module
- loading state
- exports
- constants
- names
- globals
- instruction metadata

## Project layout

A simple project can be organized like this:

```text
project/
  main.pi
  math_utils.pi
  text_utils.pi
  models/
    user.pi
    order.pi
```

`main.pi` can import nearby modules:

```pilang
import math_utils:math
import text_utils:text

print(math.clamp(120, 0, 100))
print(text.title("pilang docs"))
```

## Module exports

Export only the symbols that other modules should use.

```pilang
export fn clamp(value, min_value, max_value) {
    if value < min_value {
        return min_value
    }

    if value > max_value {
        return max_value
    }

    return value
}
```

Keep helper values private by not exporting them.

```pilang
fn normalize_number(n) {
    return n + 0
}
```

Top-level names that start with `_` are private by syntax in module import/export behavior.

## Aliases

Use short lowercase aliases for imported modules.

```pilang
import tensor:t
import string:s
import models.user:user
```

The alias keeps call sites readable:

```pilang
name = s.trim(user.display_name())
```

## Main module

The file passed to the runner is the main module.

```text
pi run main.pi
```

or:

```text
pi main.pi
```

The main module is responsible for starting the program. Other modules should mostly define reusable functions, constants, classes, and exported values.

## Avoid import side effects

When possible, modules should avoid doing expensive work at import time.

Prefer this:

```pilang
import fs:f

export fn load_config(path) {
    file = f.open(path, "r")
    text = f.read(file)
    f.close(file)

    return text
}
```

Over this:

```pilang
import fs:f

file = f.open("config.json", "r")
export config = f.read(file)
f.close(file)
```

Import-time side effects make tests, tools, and dependency order harder to reason about.

## Circular imports

The module loader tracks loading state, but circular imports should still be avoided when possible.

Problem shape:

```text
a.pi imports b.pi
b.pi imports a.pi
```

Better shape:

```text
a.pi imports shared.pi
b.pi imports shared.pi
```

Move shared constants, types, or helper functions into a third module.

## Suggested package layout

For larger projects, use a directory as the package boundary:

```text
image_tools/
  main.pi
  image_tools.pi
  filters.pi
  colors.pi
  io.pi
  tests/
    filters_test.pi
```

The package entry file can re-export the public API:

```pilang
import filters:f
import colors:c

export blur = f.blur
export sharpen = f.sharpen
export rgb = c.rgb
```

Then users can import one module instead of many internal files.

## Versioning convention

Until package metadata exists, document version information in a normal exported constant.

```pilang
export VERSION = "0.1.0"
```

For public modules, use semantic versioning:

```text
MAJOR.MINOR.PATCH
```

- Increment `MAJOR` for breaking changes.
- Increment `MINOR` for new compatible features.
- Increment `PATCH` for compatible fixes.

## Future package metadata

A future package system could add a manifest like:

```text
package name
version
entry module
dependencies
license
authors
```

That layer should build on the existing module system instead of replacing it. Source files should still be normal Pilang modules, and imports should remain understandable without hidden magic.

## Practical rules

- Keep one clear main file.
- Put reusable code in modules.
- Export intentionally.
- Use `_` for private top-level module names.
- Keep import aliases short and lowercase.
- Avoid circular imports.
- Avoid heavy import-time work.
- Document module version constants for shared code.
