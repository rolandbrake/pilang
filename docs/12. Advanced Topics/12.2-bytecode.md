# 12.2 Bytecode

Pilang bytecode is the compact instruction format executed by the VM. The compiler emits bytecode instead of directly interpreting source text.

Bytecode keeps execution simple:

- source syntax is handled once by the scanner, parser, and compiler
- the VM executes a small set of instructions
- constants and names are stored in tables and referenced by index
- jumps and call frames handle control flow

## Instruction shape

Each instruction has an opcode. Some opcodes also have operands.

Examples of opcode families:

- constants: `OP_LOAD_CONST`, `OP_PUSH_NIL`
- variables: `OP_STORE_GLOBAL`, `OP_LOAD_GLOBAL`, `OP_STORE_LOCAL`, `OP_LOAD_LOCAL`
- control flow: `OP_JUMP`, `OP_JUMP_IF_FALSE`, `OP_JUMP_IF_TRUE`, `OP_LOOP`
- calls: `OP_CALL_FUNCTION`, `OP_CALL_FUNCTION_KW`, `OP_CALL_SPREAD`
- collections: `OP_PUSH_LIST`, `OP_PUSH_MAP`, `OP_PUSH_SET`, `OP_PUSH_TUPLE`
- item access: `OP_GET_ITEM`, `OP_SET_ITEM`, `OP_GET_MEMBER`, `OP_SET_MEMBER`
- functions and closures: `OP_PUSH_FUNCTION`, `OP_PUSH_CLOSURE`, `OP_LOAD_UPVALUE`, `OP_STORE_UPVALUE`
- modules: `OP_IMPORT`, `OP_GET_EXPORT`, `OP_IMPORT_ALL`, `OP_IMPORT_DEFAULT`
- tensors: `OP_TENSOR_GET`, `OP_TENSOR_SET`

The opcode list is defined in the runtime source in `pi_opcode.h`.

## Constants table

Literal values are stored in the constants table.

```swift
message = "hello"
answer = 42
```

The string `"hello"` and number `42` can be stored once in the constants table. Bytecode instructions then refer to them by index.

This keeps the instruction stream small and avoids embedding full values directly into every instruction.

## Names table

Identifiers are stored in the names table.

```swift
let total = 0
total += 10
print(total)
```

Names such as `total` and `print` can be stored once and referenced by index when loading or storing variables.

## Stack effects

Most instructions operate on the operand stack.

For a simple expression:

```swift
result = 2 + 3
```

The bytecode behaves conceptually like:

```text
load constant 2
load constant 3
binary +
store result
```

After `binary +`, the two operands are consumed and the result is pushed.

## Jumps

Conditionals and loops are compiled using jumps.

```swift
if score >= 50 {
    print("pass")
} else {
    print("fail")
}
```

The compiler emits a conditional jump around the first branch when the condition is false, then a normal jump over the `else` branch after the first branch completes.

Loops use jumps to return to the loop condition or loop body.

```swift
while i < 10 {
    i += 1
}
```

`break` and `continue` are also compiled as jumps, with the compiler patching their target addresses after it knows where the loop exits or repeats.

## Function bytecode

Functions have their own bytecode body, constants, names, parameter names, and instruction metadata.

```swift
fn add(a, b) {
    return a + b
}
```

The outer code creates the function value. The function body runs later when the value is called.

Closures include upvalue information so the function can access captured variables.

## Keyword and spread calls

Pilang has separate bytecode support for normal calls, keyword calls, and spread calls.

```swift
draw_rect(x=10, y=20, width=50, height=30)
```

Named arguments are represented in call handling so the function can receive `kw_args`.

```swift
args = [1, 2, 3]
fn_value(*args)
```

Spread calls use dedicated call behavior to expand iterable arguments at the call site.

## Collections

Lists, maps, sets, and tuples have construction opcodes.

```swift
list_value = [1, 2, 3]
map_value = {"name": "Pilang"}
set_value = {"a", "b"}
tuple_value = tuple(1, 2, 3)
```

Comprehensions use append-style bytecode so values can be produced during iteration.

## Debug metadata

The compiler records instruction metadata, including:

- description
- source line
- source column
- bytecode offset
- function name
- opcode
- operands

This metadata is used for diagnostics and disassembly.

When the runtime is built with debug support, compiled code can be disassembled before execution.

## Reading bytecode mentally

You usually do not need exact bytecode to understand Pilang, but this model helps:

- expressions push values
- operators pop operands and push results
- assignments store stack values into locals, globals, members, or indexes
- conditions jump based on truthiness
- calls create frames
- returns pop frames
- imports load modules and exports

That model explains most runtime behavior.
