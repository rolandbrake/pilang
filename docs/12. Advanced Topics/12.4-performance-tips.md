# 12.4 Performance Tips

Pilang is dynamic and expressive, so performance depends on how much work your program asks the VM to do. The biggest wins usually come from reducing repeated allocation, avoiding unnecessary dynamic lookup, and choosing the right collection or module helper.

## Prefer local variables in hot code

Local variables are faster to access than globals because they live in stack slots.

```swift
let total = 0

fn sum(values) {
    let result = 0

    for value in values {
        result += value
    }

    return result
}
```

Inside loops and frequently called functions, keep repeated values local.

## Avoid repeated global and module lookup

If a module function is used many times, store it in a local variable.

```swift
import math:m

let sqrt = m.sqrt
let total = 0

for n in values {
    total += sqrt(n)
}
```

This avoids repeated member lookup on `m`.

## Build collections carefully

Repeatedly creating new lists can be expensive.

```swift
// Clear and direct.
result = []

for n in numbers {
    result = result + (n * 2)
}
```

For simple _transformations, `map` can be clearer:

```swift
result = map(numbers, n -> n * 2)
```

For complex loops, prefer one pass that does all required work instead of multiple passes over the same collection.

## Combine passes when useful

This is readable but walks the list twice:

```swift
evens = filter(numbers, n -> n % 2 == 0)
squares = map(evens, n -> n * n)
```

For large lists, one loop can be faster:

```swift
squares = []

for n in numbers {
    if n % 2 == 0 {
        squares = squares + (n * n)
    }
}
```

Choose the clearer version first. Combine passes when profiling or obvious scale makes it worthwhile.

## Use tensors for numeric arrays

For numeric, matrix-like, or multidimensional data, tensors are usually a better fit than nested lists.

```swift
import tensor:t

matrix = t.ones([100, 100])
scaled = t.mult(matrix, 5)
```

Tensor operations can work over compact numeric storage and avoid object-heavy nested list traversal.

## Avoid unnecessary string rebuilding

Strings are immutable-style values in normal Pilang code. Rebuilding a string repeatedly in a large loop can allocate many intermediate strings.

```swift
text = ""

for part in parts {
    text = text + part
}
```

When possible, keep data as a list during processing and join or format once at the edge.

## Cache expensive pure work

The `func` module provides `memoize` for functions that repeatedly receive the same inputs.

```swift
import func:f

fn slow_square(n) {
    return n * n
}

fast_square = f.memoize(slow_square)

print(fast_square(100))
print(fast_square(100)) // returns cached result
```

Memoization is best for pure functions: same inputs, same result, no side effects.

## Be careful with closures in loops

Closures are useful, but creating many short-lived closures in hot loops adds allocation and GC work.

```swift
for n in values {
    fn inner() {
        return n * 2
    }

    print(inner())
}
```

If the function does not need to capture loop state, define it once outside the loop.

## Keep object shapes simple

Maps and objects use dynamic lookup. This is flexible, but repeated member access is more expensive than local variables.

```swift
let x = point.x
let y = point.y

for i in range(0, 1000) {
    draw(x, y)
}
```

If a value does not change inside a hot loop, load it once.

## Use built-ins for common operations

Built-in modules are native code. Prefer them for operations they already support:

- `math` for numeric functions
- `tensor` for numeric arrays
- `col` for collection helpers
- `string` for string helpers
- `fs` for file operations
- `time` for timers and time values

## Watch recursive depth

Recursion uses call frames. Deep recursion can run into stack limits.

```swift
fn countdown(n) {
    if n == 0 {
        return nil
    }

    return countdown(n - 1)
}
```

For very deep repetition, prefer loops.

```swift
while n > 0 {
    n -= 1
}
```

## Reduce GC pressure

The garbage collector reclaims unreachable heap objects, but allocation still has a cost.

To reduce GC pressure:

- avoid creating temporary lists and maps in tight loops
- reuse long-lived objects when that keeps code clear
- keep large values local only as long as needed
- avoid accidental globals that keep objects alive for the whole module
- close files and release external resources when modules provide close functions

## Measure before rewriting

The native runner prints execution time after running a file. Use that as a simple first measurement.

```text
Execution Time: 3.4120 ms
```

For performance work:

1. Measure the current version.
2. Change one thing.
3. Measure again.
4. Keep the clearer version unless the faster version matters.
