# 12.6 PX Project Build Format

A `.px` file is Pilang's built bytecode project for one entry script and all
source modules imported by that script. For example, building `app.pi` creates
`app.px` beside it. Built-in modules, such as `net.socket`, are supplied by
the native executable and are not stored in the build.

This document defines version 1 of the format. The first implementation will
only read and write this format after serialization for each value and code
object has been added.

## Encoding rules

- All integers use little-endian encoding.
- Strings are UTF-8 and are stored without a trailing null byte.
- Offsets are byte offsets from the beginning of the file.
- Data is written field by field; C structs must not be written directly,
  because compiler padding is not part of the format.

## File layout

```text
+----------------+----------------------------------------------+
| PX header      | format identity and project-wide metadata    |
+----------------+----------------------------------------------+
| module table   | one fixed-size record per source module      |
+----------------+----------------------------------------------+
| string table   | module names and resolved source paths       |
+----------------+----------------------------------------------+
| module payload | compiled code, constants, names, debug data  |
+----------------+----------------------------------------------+
```

### PX header (56 bytes)

| Field | Type | Meaning |
|---|---:|---|
| `magic` | `u32` | `31415` — the Pilang executable file identifier. |
| `format_version` | `u16` | Build-file format version; initially `1`. |
| `header_size` | `u16` | `56`, allowing future compatible header extensions. |
| `vm_abi` | `u32` | Bytecode/serializer ABI version. A mismatch invalidates the build. |
| `flags` | `u32` | Reserved; initially `0`. |
| `project_hash` | `u64` | Hash of the ordered module source hashes. |
| `module_count` | `u32` | Number of source-module records. |
| `reserved` | `u32` | Must be `0`. |
| `module_table_offset` | `u64` | Offset of the first module record. |
| `string_table_offset` | `u64` | Offset of the shared string table. |
| `payload_offset` | `u64` | Offset of the first module payload. |

### Module table record (56 bytes)

| Field | Type | Meaning |
|---|---:|---|
| `name_offset` | `u32` | Offset in the string table of the import name, such as `app.http`. |
| `name_length` | `u32` | Length of that name. |
| `path_offset` | `u32` | Offset in the string table of the resolved `.pi` path. |
| `path_length` | `u32` | Length of that path. |
| `source_size` | `u64` | Source file size in bytes. |
| `source_hash` | `u64` | Hash of the exact source text. |
| `payload_offset` | `u64` | Offset of the module's compiled payload. |
| `payload_size` | `u64` | Size of that payload. |
| `flags` | `u32` | `PX_MODULE_ENTRY` for the project entry module; otherwise `0`. |
| `reserved` | `u32` | Must be `0`. |

## Module payload

The payload starts with three `u32` counts, followed by the top-level bytecode:

```text
u32 bytecode_size
u32 constant_count
u32 name_count
u8[bytecode_size] bytecode
constant[constant_count]
string[name_count] names
```

Constants are tagged values. Version 1 serializes `nil`, booleans, IEEE-754
numbers, strings, and nested `ObjCode` values. A nested code value contains its
bytecode, argument flags, and parameter-name strings; its constants remain in
the module's shared constant table. Unsupported constant types make a build
write fail rather than producing an incomplete build.

Instruction metadata is deliberately the next payload addition. It is useful
for disassembly and source locations but is not required for bytecode execution.
Payloads must never contain raw memory addresses, VM globals, object pointers,
or native function pointers.

## Validity

Before executing a `.px`, Pilang checks the magic number, format version,
VM ABI, entry path, and every built source module's size and hash. If any
check fails, it compiles the project normally and replaces the build.

Build a project explicitly with:

```text
pilang build program.pi
```

`build` compiles the project without executing it, then creates or refreshes
`program.px`. Normal execution uses a valid adjacent build automatically and
falls back to source compilation when it is absent or stale.
