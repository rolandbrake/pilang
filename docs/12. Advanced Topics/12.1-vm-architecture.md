# 12.1 VM Architecture

Pilang runs on a stack-based virtual machine. The compiler turns source code into bytecode, and the VM executes that bytecode instruction by instruction.

The VM keeps the active program state in a `vm_t` structure. Conceptually, it contains:

- an operand stack
- call frames
- bytecode and constants
- name tables
- global variables
- loaded modules
- open upvalues for closures
- iterator state
- heap objects tracked by the garbage collector
- instruction metadata for debugging

## Execution pipeline

Running a file follows this shape:

```text
source file
  -> scanner
  -> parser
  -> compiler
  -> bytecode
  -> VM
```

The scanner reads characters and produces tokens. The parser consumes tokens and checks that the program follows Pilang grammar. The compiler emits bytecode. The VM executes the bytecode.

## Operand stack

The operand stack stores temporary values while expressions are evaluated.

```pilang
value = (2 + 3) * 4
```

The VM can evaluate this by pushing values, applying binary operations, and leaving the final result on the stack before storing it in `value`.

The stack is also used for function calls. Arguments are pushed before a call, and return values are pushed back after a function returns.

## Call frames

Each function call creates a frame. A frame stores the execution state needed to resume the caller after the function returns:

- program counter
- stack pointer
- base pointer
- instruction pointer
- bytecode for the active function
- constants and names for that function
- the function's global environment

This allows nested calls and recursion.

```pilang
fn fact(n) {
    if n <= 1 {
        return 1
    }

    return n * fact(n - 1)
}

print(fact(5))
```

Each call to `fact` gets its own frame, but all calls share the function's compiled body.

## Globals and locals

Pilang separates global and local storage.

- Module globals live in a hash table.
- Local variables live in stack slots inside the current frame.
- Captured locals can become upvalues so closures can keep using them after the outer function returns.

```pilang
let global_name = "module"

fn make_counter() {
    let count = 0

    return fn () {
        count += 1
        return count
    }
}
```

In this example, `count` is captured by the returned function.

## Closures and upvalues

Closures work by storing references to variables from outer scopes. The VM tracks open upvalues while the outer function is still running. When a captured local would otherwise disappear from the stack, it is closed so the inner function can still read and write it.

```pilang
fn make_multiplier(factor) {
    return n -> n * factor
}

double = make_multiplier(2)
print(double(10)) // 20
```

The returned arrow function keeps access to `factor`.

## Modules

Loaded modules are cached by name and path. A module keeps:

- its name
- its file path
- loading state
- exports
- constants
- names
- instruction metadata
- global environment

The loading state prevents repeated work and helps avoid broken behavior during circular imports.

## Built-ins

Built-in functions and modules are native C functions exposed as Pilang values. They use the same call path as normal functions from the language user's point of view.

```pilang
import math:m

print(m.sqrt(25))
```

Internally, `m.sqrt` is a native function. It receives the VM, argument count, and argument array, then returns a Pilang `Value`.

## Iterators

The VM keeps iterator state for loops. Collections such as lists, strings, maps, sets, tuples, ranges, and tensors can be traversed by `for ... in`.

```pilang
for item in [1, 2, 3] {
    print(item)
}
```

Iterator state is managed separately from ordinary locals so nested loops can run correctly.

## Garbage collector

Heap-allocated values are linked into the VM object list. The garbage collector marks reachable objects from roots such as stack values, globals, frames, open upvalues, modules, and active iterators. Unmarked objects are reclaimed.

See [10.1 Garbage Collection](../10.%20Memory%20Management/10.1-garbage-collection.md) for the memory-management view.

## Native and browser builds

The native build runs source files from the command line. The Emscripten build exposes browser-callable entry points such as setting source, executing source, disassembling source, pausing, resuming, and stopping execution.

This means the same VM design can support both local execution and browser-based tooling.
